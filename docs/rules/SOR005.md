# SOR005 · unbounded-storage-growth

**Default severity:** warning  
**Category:** Storage / DoS

## What it detects

A load–grow–store sequence on a `Vec` or `Map` from `soroban_sdk` within a single function where no length guard (`.len()` check before growth) is visible.

The pattern is:
1. A local variable assigned from `storage.get(key).unwrap_or(Vec::new(env))`.
2. A growth method called on it: `push_back`, `push_front`, `insert`, or `set`.
3. The variable written back with `storage.set(key, &var)`.
4. No `.len()` comparison before step 2.

## Why it matters

Storage entries have size limits in Soroban. A `Vec` or `Map` stored under a single fixed key and appended on every call will grow without bound. Once it exceeds resource limits, every operation that reads or writes that entry fails — effectively a self-inflicted denial of service.

## Vulnerable example

```rust
// soroban-lint: vulnerable
let mut users: Vec<Address> = env.storage()
    .persistent()
    .get(&DataKey::Users)
    .unwrap_or(Vec::new(&env));
users.push_back(new_user);
env.storage().persistent().set(&DataKey::Users, &users);
```

## Safe example

```rust
// soroban-lint: safe
// Option 1: per-item keys with a counter.
env.storage().persistent().set(&DataKey::User(new_user.clone()), &true);
let count: u32 = env.storage().persistent().get(&DataKey::UserCount).unwrap_or(0);
env.storage().persistent().set(&DataKey::UserCount, &(count + 1));

// Option 2: enforce a maximum length.
let mut users: Vec<Address> = env.storage()
    .persistent()
    .get(&DataKey::Users)
    .unwrap_or(Vec::new(&env));
if users.len() >= MAX_USERS {
    return Err(Error::Full);
}
users.push_back(new_user);
env.storage().persistent().set(&DataKey::Users, &users);
```

## Configuration options

None.

## How to suppress

```rust
// soroban-lint: allow(SOR005) reason="list is bounded by external invariant enforced by the caller"
```

## Known false positives and blind spots

- Growth split across multiple functions where the collection is returned and stored externally is not detected.
- Growth performed inside a loop over caller-supplied input without an explicit bound is not detected.
- Indirect growth via a helper that receives the collection as an argument is not detected.
- The rule uses heuristics based on `Vec::new` / `Map::new` in the initializer expression; alternative initialization patterns may not be recognized.
