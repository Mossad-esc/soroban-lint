# SOR007 · unprotected-initialize

**Default severity:** error  
**Category:** Access control

## What it detects

Initializer entrypoints (matched by name from `init_names`) that write to storage without BOTH:

- **(a)** An already-initialized guard: a `has()` or `get()` on a storage key in the same function that leads to an early `return` or error.
- **(b)** A `require_auth` call (directly or via the call graph).

The rule flags only when **neither** protection is present. Having only one of the two is allowed but discouraged (see below).

## Why it matters

An initializer that can be called by anyone, or called twice, lets an attacker seize ownership or reset configuration after legitimate deployment.

## Vulnerable example

```rust
// soroban-lint: vulnerable
pub fn initialize(env: Env, admin: Address) {
    env.storage().instance().set(&DataKey::Admin, &admin);
}
```

## Safe example

```rust
// soroban-lint: safe
pub fn initialize(env: Env, admin: Address) -> Result<(), Error> {
    if env.storage().instance().has(&DataKey::Admin) {
        return Err(Error::AlreadyInitialized);
    }
    admin.require_auth();
    env.storage().instance().set(&DataKey::Admin, &admin);
    Ok(())
}
```

## Having only one protection

- **Guard only (no auth):** Prevents re-initialization but allows anyone to call it first. Acceptable in some deployment models where the initializer is called atomically in the deployment transaction, but generally discouraged.
- **Auth only (no guard):** Prevents unauthorized calls but allows a privileged caller to re-initialize and reset state. Uncommon but possible in intentionally upgradeable designs.

Neither case is flagged by SOR007 (only the case where both are absent is flagged), but a security review should confirm the design intent.

## Configuration options

```toml
[rules.SOR007]
enabled = true
severity = "error"
# Function names considered initializers (case-insensitive exact match)
init_names = ["initialize", "init", "setup"]
```

## How to suppress

```rust
// soroban-lint: allow(SOR007) reason="deployer guarantees single-call via atomic deploy+init"
pub fn initialize(env: Env, admin: Address) {
    env.storage().instance().set(&DataKey::Admin, &admin);
}
```

## Known false positives and blind spots

- The rule uses name matching. Functions with non-standard initializer names that are not in `init_names` are not checked.
- The guard detection looks for `has()` or `get()` on storage in the same function body followed by an early exit. Guards delegated to a helper function are not currently detected.
- The rule does not distinguish between `instance()` and `persistent()` storage for guard matching.
