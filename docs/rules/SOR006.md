# SOR006 · panic-in-entrypoint

**Default severity:** warning  
**Category:** Error handling

## What it detects

Panic-producing patterns in public entrypoints and helpers reachable from them:

- `.unwrap()` — panics when the value is `None` or `Err`.
- `.expect(msg)` — panics with a message.
- `panic!(…)` macro.
- `unreachable!(…)` macro.
- `todo!(…)` macro.
- `unimplemented!(…)` macro.
- Direct indexing with a non-constant index: `collection[idx]`.

## Why it matters

Panics produce opaque failures. On Soroban, a panicking contract returns an untyped error that callers cannot match against. A `#[contracterror]` enum gives callers and integrators meaningful, stable error codes and makes error behavior explicit in the contract ABI.

## Vulnerable example

```rust
// soroban-lint: vulnerable
let admin: Address = env.storage().instance().get(&DataKey::Admin).unwrap();
```

## Safe example

```rust
// soroban-lint: safe
let admin: Address = env
    .storage()
    .instance()
    .get(&DataKey::Admin)
    .ok_or(Error::NotInitialized)?;
```

## Configuration options

None. `assert!` and `assert_eq!` are not flagged in this version. If that becomes
necessary, a `check_asserts` toggle could be added in a future release.

## How to suppress

```rust
// soroban-lint: allow(SOR006) reason="unreachable! is proven by invariant X"
unreachable!("variant Y is never constructed after migration");
```

## Known false positives and blind spots

- `assert!` and `assert_eq!` are not flagged. Some SDK examples use `assert!` as a guard; flagging those would create excessive noise. This may be revisited.
- The rule does not track whether an `unwrap` is inside an infallible branch (e.g., after an `is_some()` check). This can produce false positives on carefully written code.
- Direct indexing with a `const` or uppercase identifier index is not flagged (treated as safe). This heuristic may miss non-conventional constant names.
